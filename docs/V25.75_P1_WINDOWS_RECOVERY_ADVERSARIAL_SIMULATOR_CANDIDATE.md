Date: 2026-08-24

## Purpose

Close a PID-reuse trust-boundary in bounded UAC recovery without expanding elevation authority and without substituting source/synthetic proof for real Windows validation.

## Defect found by independent review

The prior helper revalidated only PID + executable name immediately before launching fixed-system `taskkill.exe`. If the original process exited and Windows reused the PID for a new process with the same allowed image name (`Codex.exe` or `ChatGPT.exe`), name-only validation could not distinguish the new process incarnation.

## Runtime hardening

`_runtime/HMS_Codex_WindowsOneShotElevation.py` now requires an expected identity for every elevation target:

- PID;
- canonical supported image name;
- process creation FILETIME represented as `creation_time_100ns`.

The helper:

1. captures supported identities from an opened process object using `QueryFullProcessImageNameW` + `GetProcessTimes`;
2. reopens each target with `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`;
3. rejects name/creation-time mismatch as `WINDOWS_ELEVATION_TARGET_IDENTITY_CHANGED`;
4. keeps the validated process handle open through the entire UAC prompt and fixed `taskkill.exe` execution;
5. verifies termination through the original process handle rather than re-identifying by PID after close;
6. releases the process-object handles only after UAC/taskkill completes or fails.

Holding the process-object handle is the PID-reuse barrier: the PID cannot be recycled while that object remains referenced. The helper still elevates only the fixed system `taskkill.exe`, accepts numeric PID arguments only, preserves the 32-PID bound and one-shot token, and introduces no PowerShell/cmd/generic elevated command path.

## GUI / official-auth lifecycle

`_runtime/HMS_GUI_RECOVERY_ENTRY.pyw` now captures process identities rather than PID-only lists for UAC-eligible recovery.

For official-auth switching:

- same PID + same image + same creation time = original client still survives;
- same PID + same allowed image but different creation time = a new process, not the original client;
- identity discovery failure returns `IDENTITY_DISCOVERY_FAILED` and is non-elevatable;
- UAC targets only the surviving original identity map;
- post-commit auth success remains preserved if identity/UAC close fails.

## Validation / session bundle

`_runtime/HMS_Codex_WindowsUACRecoveryValidation.py` uses identity-bound target discovery and passes expected identities into both first attempt and same-token replay.

`_runtime/HMS_Codex_WindowsUACValidationBundle.py` now requires:

- identity binding ready at session init;
- identity binding observed in both Cancel and Close case reports;
- Close evidence to report `pid_reuse_blocked_by_open_handles = true`;
- the existing exact Cancel/Close verdicts, replay block, host/source/session binding, effect boundary and positive close count.

The pair remains recovery validation only; it is not canonical production evidence.

## Adversarial simulator

`_runtime/HMS_Codex_WindowsRecoveryAdversarialSimulator.py` now uses a deterministic synthetic PID range away from `os.getpid()` and covers:

- same-name PID reuse with changed creation time;
- different-image PID substitution;
- missing/malformed identity binding;
- duplicate/current/invalid and 32/33 PID bounds;
- policy unknown/not-requested/restart-disabled;
- identity-discovery failure;
- old/new process-incarnation lifecycle;
- UAC one-shot/replay boundaries;
- redaction/classification and quiet background behavior;
- explicit proof that the simulator itself never enumerates real processes, opens real process handles or invokes real UAC/taskkill.
