## Purpose

Close bounded-UAC process targeting trust boundaries without expanding elevation authority and without substituting source/synthetic proof for real Windows validation.

## Defects found by independent review

The candidate now closes four distinct gaps:

1. PID + executable-name revalidation could not distinguish a newly created `Codex.exe`/`ChatGPT.exe` that reused an old PID.
2. `taskkill /T` expanded elevated effects to child processes that had never passed the allowlist or identity checks.
3. A non-zero `taskkill.exe` exit could previously be confused with success if a target happened to exit independently.
4. PID/name/creation binding alone did not prevent targeting a supported-name process in a different Windows logon/session.

## Runtime hardening

`_runtime/HMS_Codex_WindowsOneShotElevation.py` now binds every elevation target to:

- PID;
- canonical supported image name;
- process creation FILETIME as `creation_time_100ns`;
- Windows `session_id`.

The helper:

1. discovers supported targets only in the HMS process's current Windows session;
2. captures identity using `QueryFullProcessImageNameW`, `GetProcessTimes` and `ProcessIdToSessionId`;
3. reopens targets with `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`;
4. rejects session mismatch/change before UAC effect execution;
5. rejects name/creation-time mismatch as an identity change;
6. keeps validated process handles open through UAC and fixed-system `taskkill.exe`, preventing PID reuse while the operation is live;
7. verifies termination through the original process handles;
8. requires `taskkill.exe` exit code `0`;
9. releases process-object handles only after completion/failure.

Elevated arguments are limited to exact validated PIDs plus `/F`. `/T` is prohibited, so child-process trees are outside elevation authority. The helper still uses only fixed system `taskkill.exe`, preserves the 32-PID bound and one-shot token, and introduces no generic PowerShell/cmd/elevated executable path.

## Caller authority audit

`_runtime/HMS_Codex_WindowsElevationCallerAudit.py` statically audits runtime Python/PYW files that reference `elevated_close_supported_processes`.

It requires GUI and bounded-harness callers to be present, every helper call to provide explicit `expected_identities=...`, direct-import aliases to remain auditable, dynamic `getattr` access to be rejected, and dynamic `**kwargs` not to substitute for the explicit identity argument.

The Windows workflow compiles and executes this audit as a dedicated required proof step.

## GUI / official-auth lifecycle

`_runtime/HMS_GUI_RECOVERY_ENTRY.pyw` tracks process-incarnation identity maps. Because helper discovery is current-session filtered and identity comparison includes `session_id`:

- same PID + image + creation + session = original client still survives;
- changed creation time = new process;
- changed Windows session = not the original client;
- identity discovery failure is non-elevatable;
- UAC targets only surviving original identities;
- post-commit auth success remains preserved if close recovery fails.

## Validation / session bundle / operator runner

`_runtime/HMS_Codex_WindowsUACRecoveryValidation.py` now requires current-session identity readiness before interactive execution. A successful Close requires helper evidence for identity binding, Windows-session binding, open-handle PID-reuse blocking and a positive close count. Cancel remains valid without claiming a returned `session_bound=true` effect result because UAC cancellation exits the helper by exception; it does record that a current-session-bound identity map was used.

`_runtime/HMS_Codex_WindowsUACValidationBundle.py` now requires identity + Windows-session readiness at session init, requires both case reports to record session-bound identity usage, and requires Close to report `session_bound=true` plus the PID-reuse guard. The final pair declares both `identity_binding_required=true` and `session_binding_required=true`.

`_runtime/HMS_Run_UAC_Validation.ps1` fails immediately when any of those predicates are missing.

The bounded pair remains recovery validation only; it is not canonical production evidence.

## Adversarial simulator

The Windows workflow also runs this simulator as a dedicated proof step.
