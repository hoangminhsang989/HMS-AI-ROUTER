# HMS-AI-ROUTER — v25.75 P1 UAC Runtime Validation Harness Checkpoint

Date: 2026-08-24

## Purpose

This increment adds a bounded real-Windows recovery validation harness that is explicitly separate from the canonical seven-case production certification.

File:

`_runtime/HMS_Codex_WindowsUACRecoveryValidation.py`

The harness has three modes with different authority/effect boundaries.

## `proof`

Source/synthetic only.

- No Windows process mutation.
- No UAC prompt.
- No Codex/ChatGPT close.
- Validates acknowledgement ordering, preflight isolation, one-shot replay logic, production-authority denial and absence of a generic elevation command in the harness.
- This is the only harness mode executed by GitHub Actions.

## `preflight`

Read-only Windows runtime inspection.

It checks:

- supported `Codex.exe` / `ChatGPT.exe` PID discovery;
- existence/resolution of the fixed Windows `System32\taskkill.exe` target through the elevation helper;
- current structured `CodexLaunchAfterAuthSwitch` and `RestartCodexOnSwitch` policy via backend `get_settings`;
- whether the interactive validation prerequisite is currently met.

It never calls the elevated close helper and never opens a UAC prompt.

Only the two required policy booleans are reported; the complete settings document is not persisted in the validation report.

## `interactive`

This is an explicit effectful validation command and cannot run without the exact acknowledgement:

`I_UNDERSTAND_CODEX_OR_CHATGPT_MAY_CLOSE`

When acknowledged:

1. discover currently running supported Codex/ChatGPT PIDs;
2. generate a fresh one-shot token;
3. invoke the existing fixed-taskkill elevation helper;
4. classify the first result;
5. immediately call the helper again with the **same token** to prove replay rejection in the same process;
6. report the remaining supported-client PID set.

The possible successful runtime verdicts are intentionally narrow:

- `PASS_CANCEL_AND_REPLAY_BLOCK`: Windows UAC was presented, the operator cancelled, and replay with the same token was blocked.
- `PASS_CLOSE_AND_REPLAY_BLOCK`: Windows UAC was presented, at least one supported client PID was actually closed, and replay with the same token was blocked.

If the target client exits by itself after discovery but before UAC, the harness records `ALREADY_CLOSED_BEFORE_UAC` and **does not** count this as a successful close validation.

Other results are `PARTIAL_REPLAY_BLOCKED`, `BLOCKED` or `FAIL` as appropriate.

## Output rules

- JSON is always printed to stdout.
- File output is optional and only happens when the operator supplies `--output`.
- No default evidence directory is mutated.
- Runtime validation reports explicitly set:
  - `windows_runtime_certified = false`;
  - `production_evidence_eligible = false`;
  - `production_score_mutation_authorized = false`;
  - `canonical_seven_case_certification = false`.

## Next operational gate

On the authorized Windows target, the intended sequence is:

1. run `preflight`;
2. with a supported client running, run one `interactive` validation and deliberately cancel the UAC prompt to obtain the cancel/replay result;
3. start the supported client again if needed;
4. run a second `interactive` validation and approve UAC to obtain the close/replay result;
5. separately verify restart-disabled/not-requested policy behavior through the product GUI;
6. keep all resulting recovery evidence separate from the canonical seven-case production packet.

No production evidence score may be changed from these recovery validation results alone.
