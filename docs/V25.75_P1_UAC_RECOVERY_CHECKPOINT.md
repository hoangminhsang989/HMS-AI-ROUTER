# HMS-AI-ROUTER — v25.75 P1 One-shot Windows UAC Recovery Checkpoint

Date: 2026-08-24

## Scope

This increment completes the first **executable one-shot UAC recovery path** for the Codex-only product without introducing a generic elevated command runner.

It follows the restricted safety pattern audited from Cockpit Tools `v1.3.28`: revalidate supported client PIDs, elevate the fixed Windows `taskkill.exe` binary only, wait for completion, verify targets are gone, and retry the original operation through its normal transaction/verifier path.

This is still source/CI-proof work. No real UAC prompt or real client process termination is claimed from the repository proofs.

## Delivered

### 1. Codex-only one-shot elevation helper

`_runtime/HMS_Codex_WindowsOneShotElevation.py`:

- supports only process names `Codex.exe` and `ChatGPT.exe`;
- rejects generic processes such as Explorer/Notepad;
- accepts at most 32 non-zero PIDs and excludes the current HMS process;
- re-enumerates Windows processes immediately before elevation and revalidates every still-running target name;
- resolves `%SystemRoot%\System32\taskkill.exe` through the Windows system-directory API rather than accepting a caller executable path;
- constructs arguments only from validated numeric PIDs plus `/T /F`;
- invokes `ShellExecuteExW` with `runas` only for that fixed system binary;
- waits at most 120 seconds;
- maps Windows error 1223 to `WINDOWS_ELEVATION_CANCELLED`;
- verifies no targeted Codex/ChatGPT process remains after the elevated helper exits;
- exposes no CLI entrypoint for arbitrary elevation.

### 2. One-shot operation token

Each elevation operation requires a generated token matching a bounded token format.

The helper consumes the token **before** process validation/UAC launch. Therefore:

- UAC cancellation consumes the token;
- launch failure consumes the token;
- a second prompt using the same operation token is rejected;
- the GUI must start a new explicit operation epoch before another UAC authorization can be offered.

This prevents a recovery loop from repeatedly prompting for elevation.

### 3. Structured HMS client-close recovery category

`_runtime/HMS_Codex_WindowsRecoveryContract.py` now recognizes the existing backend code:

`CODEX_RESTART_REQUIRED:`

as `CLIENT_CLOSE_BLOCKED`.

This category is recoverable and may be UAC-eligible only when:

- the operation is on the narrow close-lifecycle allowlist;
- supported Codex/ChatGPT PIDs were independently discovered;
- the UAC action has not already been consumed.

`CODEX_CLIENT_START` remains explicitly non-elevatable. Program-missing recovery never becomes UAC just because a target path exists.

### 4. Pre-mutation router transaction recovery

`_runtime/HMS_GUI_RECOVERY_ENTRY.pyw` now allows one-shot UAC only for backend `enable` / `disable` failures whose stable error code is `CODEX_RESTART_REQUIRED`.

Those errors originate from the existing Codex restart barrier before router/provider configuration mutation. The flow is:

1. original `enable` / `disable` reaches the normal backend restart barrier;
2. backend returns `CODEX_RESTART_REQUIRED` without completing the mutation;
3. recovery wrapper discovers live `Codex.exe` / `ChatGPT.exe` PIDs;
4. top-level dialog may expose `XIN QUYỀN WINDOWS 1 LẦN`;
5. user must explicitly select it;
6. token is marked consumed;
7. one-shot helper revalidates PIDs and elevates fixed `System32\taskkill.exe` only;
8. after successful close, the wrapper retries the original backend operation;
9. all existing backend verification remains authoritative.

Unrelated Access Denied errors, backup/export failures, `open_codex` start failures and background probes cannot enter this UAC path.

### 5. Official auth switch boundary remains fail-closed

The GUI wrapper is prepared to use the same one-shot close path if official auth switch returns the stable `CODEX_RESTART_REQUIRED` failure code.

However the current PowerShell official-auth path can successfully commit credentials and return a manual-restart message when post-switch client close/relaunch does not complete. That success-with-guidance case does not currently expose structured `canElevate + PID` metadata.

Therefore this checkpoint does **not** claim full one-shot UAC parity for that specific post-switch success path. It deliberately does not infer elevation eligibility from an arbitrary success message or from “Access Denied + some Codex process exists”.

The new proofs assert:

- exact Codex/ChatGPT process allowlist;
- generic process rejection;
- numeric PID-only taskkill arguments;
- fixed system taskkill resolution;
- no PowerShell/cmd/subprocess generic elevation runner;
- one-shot token replay rejection;
- UAC cancellation/timeout codes;
- no production certification or score authority;
- UAC only at the pre-mutation close barrier and never for unrelated Access Denied errors.
