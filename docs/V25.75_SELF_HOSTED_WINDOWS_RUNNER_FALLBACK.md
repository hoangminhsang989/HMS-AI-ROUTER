## Critical trust boundary

Self-hosted runners execute workflow code directly on the host. The Windows runner must therefore be treated as privileged project infrastructure.

Rules:

- never make the ordinary PR workflow permanently self-hosted;
- never treat a custom runner label as authorization;
- keep the runner offline outside one frozen qualification window;
- freeze the exact PR head before bringing the runner online;
- review the canonical Windows workflow blob at that exact head;
- accept no unreviewed pushes while the runner is online;
- stop/remove runner registration after qualification;
- never persist a runner registration token in repository files, workflow YAML, docs, issues, `.env`, or shell profiles.

- custom label `hms-ai-router-windows`;

- foreground-only execution, never persistent service mode.

It rejects reparse/junction redirects and non-empty prior runner directories. The registration token is read only from process environment variable `HMS_GITHUB_RUNNER_TOKEN`, removed before runner configuration, and never written into project artifacts.

Only the official latest `actions/runner` Windows x64 release is accepted. The bootstrap verifies release tag, exact asset name, official release namespace, positive byte size, GitHub-published SHA-256 digest, downloaded byte length and downloaded SHA-256 before extraction.
