# HMS-AI-ROUTER — v25.75 P1 Windows Recovery UX Checkpoint

Date: 2026-08-24

## Scope

This increment is a **partial source-parity tranche** against the Windows recovery UX behavior audited from Cockpit Tools `v1.3.28`. It does not change the frozen production-evidence boundary and it does not claim complete v1.3.28 parity.

## Delivered

### 1. Unified Windows recovery contract

`_runtime/HMS_Codex_WindowsRecoveryContract.py` classifies recoverable Windows failures into:

- `ACCESS_DENIED` including Windows error 5 / WSAEACCES 10013 patterns;
- `FILE_IN_USE` including Windows error 32 / sharing-violation patterns;
- `PROGRAM_MISSING` including Windows error 2 / executable-not-found patterns;
- `OTHER` for unclassified failures.

Interactive recoverable operations may expose:

- retry;
- operator handled the external cause, then retry;
- open target location when a target path is available;
- copy sanitized error detail;
- cancel.

Background probe/health/quota/refresh-style operations remain quiet and do not surface recovery dialogs.

### 2. Sanitized recovery diagnostics

Recovery detail removes common credential/token patterns, bearer values, JWT-like values, API-key-like values, email local parts and the Windows user component of `C:\Users\...` before it is displayed/copied by the recovery layer.

The recovery layer does not persist raw error text as recovery evidence.

### 3. Recovery dialog

`_runtime/HMS_Codex_WindowsRecoveryDialog.py` provides the top-level recovery surface with Vietnamese actions:

- `THỬ LẠI`;
- `ĐÃ XỬ LÝ → THỬ LẠI`;
- `MỞ VỊ TRÍ`;
- `SAO CHÉP LỖI`;
- `ĐÓNG`.

A UAC-request action exists in the contract/dialog surface only when a future caller explicitly marks an allowlisted supported-client operation eligible. The dialog itself does not execute elevation.

### 4. Recovery-first principal GUI wrapper

`_runtime/HMS_GUI_RECOVERY_ENTRY.pyw` loads the existing sealed reviewer wrapper and preserves `review.legacy` as the GUI authority, then adds bounded recovery handling for user-triggered backend operations.

Recovery is wired for interactive backend actions including the normal `open_codex` path. Official account-switch completion also receives recovery handling.

Retry is bounded to three recovery attempts. Unknown/background actions remain non-interactive.

### 5. Fail-closed launcher chain

`HMS_AI_ROUTER.vbs` now prefers:

`HMS_GUI_RECOVERY_ENTRY.pyw` → `HMS_GUI_REVIEW_ENTRY.pyw` → `HMS_GUI_SAFE_FALLBACK.pyw` → `HMS_GUI.pyw`.

It still never falls directly to `HMS_GUI_ENTRY.pyw`, preserving the prior promotion-review fail-closed boundary.

### 6. Proof and Windows CI graph

The recovery contract, recovery dialog, recovery GUI wrapper and recovery-first launcher-chain checks are now part of `.github/workflows/v2575-promotion-safety-windows.yml` compile/proof coverage.

Two proof self-match hazards were corrected before merge preparation by scoping forbidden-operation checks to implementation source before the proof function itself.

## UAC boundary — intentionally not complete yet

The recovery contract contains a narrow supported-client operation allowlist and a one-shot operation-token gate, but **no production GUI caller currently marks itself `supported_client=true` and no recovery module executes UAC**.

Therefore this checkpoint must not be described as full Cockpit v1.3.28 Windows recovery parity. The remaining P1 gap is a dedicated, narrowly allowlisted Windows elevation launcher with one-shot user-request semantics and a verifiable executable target. It must not become a generic command elevation facility.
