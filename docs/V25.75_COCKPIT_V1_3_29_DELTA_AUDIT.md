## Confirmed Codex delta from upstream changelog/source

### A. OAuth / device authorization — parity delta

v1.3.29 adds a second Codex authorization path using device code rather than local callback port `1455`.

Observed source-level changes in `crates/cockpit-core/src/modules/codex_oauth.rs` include:

- new device user-code endpoint `https://auth.openai.com/api/accounts/deviceauth/usercode`;
- new device token polling endpoint `https://auth.openai.com/api/accounts/deviceauth/token`;
- verification URL `https://auth.openai.com/codex/device`;
- 15-minute device timeout and bounded polling/request timeouts;
- pending device auth is intentionally not restored after process restart;
- browser OAuth and device auth share the login-state authority but device flow does not bind local callback port `1455`;
- connector scopes are added to OAuth: `api.connectors.read` and `api.connectors.invoke`;
- `ID_TOKEN_REFRESH_LEAD_SECONDS` changes from 15 minutes to 10 minutes.

HMS impact: existing browser OAuth is not automatically invalid, but full v1.3.29 parity now has a device-auth capability gap and an OAuth-scope/refresh-policy delta that must be explicitly accepted, implemented, or documented before baseline adoption.

### B. Quota refresh / refresh-token ownership — high-priority parity delta

Upstream changelog states quota refresh now requires only a valid access token and does not rotate the refresh token merely because the ID token is nearing expiry or a proactive keepalive interval elapsed. When the official client owns the refresh token, current quota may still be fetched with a valid access token; while waiting for a newer access token, the previous quota is retained instead of surfacing an internal refresh-token ownership condition as quota failure.

HMS impact: this touches the canonical `quota` evidence case and account-health/failover semantics. It is a **P0 parity audit item before any new production evidence epoch**.

Required HMS reconciliation questions:

1. Can quota observation succeed from a valid access token without acquiring/rotating the refresh token?
2. Does an official-client-owned refresh token remain untouched by background HMS quota probes?
3. If a newer access token is temporarily unavailable, is previous known quota retained rather than converted to an account failure?
4. Can background quota probing remain silent/non-mutating while official Codex/ChatGPT owns credential rotation?

### C. OAuth credential ownership for combined profiles — high-priority parity delta

v1.3.29 fixes standalone OAuth launches becoming falsely expired after binding the OAuth account to an API Key account. Combined profiles retain the actual OAuth credential owner and recover the latest tokens rotated by the official client; rebinding/moving instances avoids reuse of an old refresh token while preserving API Key provider configuration.

HMS impact: this intersects account switching, credential freshness, official-client ownership, failover, and the rule that source/runtime observations must not overwrite newer official credentials. It is a **P0/P1 parity audit item**.

### D. Unified Codex launch preview — parity feature delta

v1.3.29 adds a pre-launch dialog across OAuth accounts, API Keys and local API Service with account/quota/usage/target-instance state; target instance/runtime speed; model visibility/defaults; per-model reasoning/context/compaction; session visibility repair; account actions; and explicit Switch vs Switch-and-Start confirmation.

HMS impact: no current production authority should be inferred from this UI feature. The important safety semantic is that client state changes occur only after explicit confirmation. Existing HMS official-auth/recovery transactions should be checked against that confirmation-before-mutation invariant.

### E. Session repair and provider migration — parity feature/safety delta

v1.3.29 adds full provider migration/catalog repair across session and archived-session metadata and changes quick session repair to official sidebar visibility rules using the target instance's official `state_5.sqlite` and referenced rollouts. Provider discovery is narrowed to `config.toml` and official `state_5.sqlite` rather than scanning rollout history.

HMS impact: this is a significant repair/migration feature delta. It must remain non-production-authoritative until rollback/backups, selected-scope behavior, stopped-target protection and provider-bound filtering are independently reconciled.

### F. API Service / Realtime / expanded request transport — parity feature delta

v1.3.29 adds Live/Realtime APIs, WebRTC/sideband/Realtime WebSocket control, client secrets and session/transcription operations, plus Responses WebSocket transport, reasoning replay, Multi-Agent V2 and expanded model catalog behavior.

HMS impact: this is a large API-service parity workstream. It is not evidence that current HMS Windows runtime or production score improves. Adoption requires separate source/runtime tests and scope decision.
