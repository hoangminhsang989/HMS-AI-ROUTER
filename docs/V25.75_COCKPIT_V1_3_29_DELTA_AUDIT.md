## Confirmed Codex delta from upstream changelog/source

### A. OAuth / device authorization — parity delta

v1.3.29 adds a second Codex authorization path using device code rather than local callback port `1455`.

Observed source-level changes in `crates/cockpit-core/src/modules/codex_oauth.rs` include:

- new device user-code endpoint `https://auth.openai.com/api/accounts/deviceauth/usercode`;
- new device token polling endpoint `https://auth.openai.com/api/accounts/deviceauth/token`;
- verification URL `https://auth.openai.com/codex/device`;
- 15-minute device timeout and bounded polling/request timeouts;
- pending device auth is intentionally not restored after process restart;
- browser OAuth and device auth share the login-state authority but device flow does not bind local callback port `1455`;
- connector scopes are added to OAuth: `api.connectors.read` and `api.connectors.invoke`;
- `ID_TOKEN_REFRESH_LEAD_SECONDS` changes from 15 minutes to 10 minutes.

HMS impact: existing browser OAuth is not automatically invalid, but full v1.3.29 parity still has a device-auth capability gap and an OAuth-scope/refresh-policy delta that must be explicitly accepted, implemented, or documented before baseline adoption.

### B. Quota refresh / refresh-token ownership — P0 SOURCE-CLOSED, PROOF-WIRED

The exact v1.3.29 runtime caller chain is now source-certified as:

`refresh_all_quotas_for_background → refresh_all_quotas_with_options(true) → refresh_account_quota → refresh_account_quota_once → codex_account::prepare_account_for_quota_query`.

The source-level invariants are:

1. background refresh explicitly excludes account IDs reported by `running_codex_oauth_account_ids`, so an OAuth account currently owned by the official runtime is not selected for background quota refresh;
2. `prepare_account_for_quota_query` is a quota-specific helper introduced after v1.3.28;
3. a non-expired `access_token` returns before the `quota-query` cross-process refresh-token lock is acquired;
4. when access is expired, the helper acquires the lock, reloads the account, resolves official-runtime refresh ownership, synchronizes live authority when appropriate, and re-checks access-token expiry before any refresh-token rotation path;
5. `managed_account_tokens_need_refresh` is access-token-only; expired/near-expiry ID token is not sufficient to force the generic managed refresh predicate;
6. upstream tests include `expired_id_token_does_not_force_refresh_when_access_token_is_fresh` and `id_token_within_refresh_lead_does_not_force_refresh_when_access_token_is_fresh`.

HMS source verdict for this P0: **CLOSED at exact-source level**. A valid access token is sufficient for quota and the proven background path does not seize an official-runtime refresh-token chain.

Executable HMS proof is `_runtime/HMS_Codex_CockpitV1329P0ParityProof.py`. It pins the exact commits/blobs above, verifies the caller/control-flow anchors, and includes adversarial transition checks for:

- valid access token → refresh helper/rotation/credential write are prohibited;
- running official OAuth → background probe is not selected;
- newer access token appears after authority sync → it is reused without refresh-token rotation.

The proof is imported and fail-closed by `_runtime/HMS_Codex_ExternalWindowsSourceBindingProof.py`, which is already an executed step in the canonical Windows Promotion Safety workflow. Therefore this P0 is **PROOF-WIRED**, but it is not an executable CI PASS until a workflow run actually materializes and executes the step.

### C. OAuth credential ownership for combined profiles — P0 SOURCE-CLOSED, PROOF-WIRED

v1.3.29 introduces explicit credential-owner metadata in `CodexManagedAuthProjection`:

- `credential_account_id`;
- `credential_email`;
- `credential_token_generation`.

The combined API-Key/OAuth writer separates the two authorities:

1. OAuth `auth.json`/keychain material is written from the bound OAuth account;
2. provider/configuration override remains owned by the API-Key runtime account;
3. the managed projection persists the API-Key runtime owner and the OAuth credential owner together;
4. bound-account refresh resolves and validates `bound_oauth_account_id` before credential refresh.

Exact upstream v1.3.29 tests cover the safety properties directly:

- `api_key_bound_oauth_projection_tracks_runtime_and_credential_owners`;
- `bound_oauth_rotation_sync_preserves_api_key_provider_config`;
- `managed_bound_oauth_accepts_rotated_rt_without_last_refresh`;
- `persisted_credential_owner_survives_api_key_unbind_for_later_oauth_sync`;
- `legacy_combined_projection_is_recovered_and_upgraded_after_unbind`;
- generation-aware refresh behavior includes a test where a newer token generation is reused rather than consuming a rotated refresh token again.

These prove that a newer official-client credential generation remains authoritative while provider configuration stays attached to the API-Key runtime profile, including after unbind and legacy projection upgrade.

HMS source verdict for this P0: **CLOSED at exact-source level**. The stale refresh-token revival transition is prohibited by owner-aware projection plus newer-generation authority selection.

The same `_runtime/HMS_Codex_CockpitV1329P0ParityProof.py` contains adversarial transition checks that require:

- runtime owner remains the API-Key account;
- credential owner remains the OAuth account;
- newer authority generation wins;
- stale refresh token cannot be reactivated.

This proof is transitively fail-closed through the canonical source-binding proof. Status is **PROOF-WIRED / CI EXECUTION PENDING**.

HMS impact: this is a significant repair/migration feature delta. It must remain non-production-authoritative until rollback/backups, selected-scope behavior, stopped-target protection and provider-bound filtering are independently reconciled.
