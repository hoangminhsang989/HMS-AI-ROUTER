### P0-1 — quota / refresh-token ownership: SOURCE-CLOSED, PROOF-WIRED

Exact v1.3.29 runtime chain:

`refresh_all_quotas_for_background → refresh_all_quotas_with_options(true) → refresh_account_quota → refresh_account_quota_once → codex_account::prepare_account_for_quota_query`.

Source invariants:

1. background quota refresh excludes IDs in `running_codex_oauth_account_ids`;
2. `prepare_account_for_quota_query` is absent from the v1.3.28 source and is quota-specific in v1.3.29;
3. a valid `access_token` returns before the `quota-query` refresh-token lock;
4. after lock/reload, official-runtime ownership is resolved and live authority is synchronized when applicable;
5. access-token expiry is re-checked after synchronization, so a newly written valid access token is reused rather than rotating the refresh token again;
6. `managed_account_tokens_need_refresh` is access-token-only; upstream tests explicitly cover expired/near-expiry ID token not forcing refresh while access token is fresh.

HMS verdict: **P0-1 SOURCE-CLOSED**. The executable HMS proof also models fail-if-refresh semantics for valid access, official-runtime background exclusion, and post-sync access-token reuse.

## OAuth runtime reconciliation correction

The initial delta classification treated connector scopes and the 15→10 minute ID-token refresh lead as if they were new v1.3.29 Tauri-runtime behavior. Exact release-to-release source comparison narrows that claim.

### `src-tauri` runtime

v1.3.28 `src-tauri/src/modules/codex_oauth.rs` blob:

- `a4286214e7ea3f505f2a7100fbf1f03aa1e38b27`

v1.3.29 blob:

- `7a4573d8423306570eda0922644709a6b3787e6f`

Both v1.3.28 and v1.3.29 `src-tauri` runtime sources already use:

- scopes `openid profile email offline_access api.connectors.read api.connectors.invoke`;
- `ID_TOKEN_REFRESH_LEAD_SECONDS = 10 * 60`.

Therefore connector read/invoke scopes and the 10-minute lead are **not new Tauri-runtime semantics in the v1.3.28→v1.3.29 release delta**.

### `cockpit-core` synchronization

`crates/cockpit-core/src/modules/codex_oauth.rs` does change between the two releases:

- v1.3.28 blob `be401c3b5cdacb65fa88d09ece722aa3157ee509`: base scopes only and 15-minute lead;
- v1.3.29 blob `54f7f0dd7d3f34424dc53933c1fd9535e5cba1ef`: connector scopes and 10-minute lead.

This is a real **core-library source synchronization delta**, but it must not be mislabeled as a newly introduced Tauri behavior when the v1.3.28 Tauri implementation already had the same runtime values.

HMS adoption consequence: connector scopes / 10-minute lead remain documented source differences for any consumer of `cockpit-core`, but they are no longer treated as an unresolved new behavior of the canonical Tauri runtime.

## Device-code OAuth — real v1.3.29 runtime delta

Device authorization is absent from v1.3.28 `src-tauri` OAuth/command/service surfaces and is present in v1.3.29.

Exact v1.3.29 runtime behavior includes:

- user-code endpoint `https://auth.openai.com/api/accounts/deviceauth/usercode`;
- token polling endpoint `https://auth.openai.com/api/accounts/deviceauth/token`;
- verification URL `https://auth.openai.com/codex/device`;
- exchange redirect `https://auth.openai.com/deviceauth/callback`;
- 15-minute device-flow deadline;
- bounded HTTP requests;
- server-provided poll interval with a default fallback;
- a single shared OAuth login-state authority: a second device flow is rejected while a login session exists;
- device state is intentionally not restored from disk after restart, preventing a stale device code from being revived as a callback flow;
- device polling exits when its login/device state is no longer active;
- completion reuses the common OAuth code-exchange path with the device exchange redirect;
- cancellation is login-ID aware.

Runtime reachability is source-proven:

`src/services/codexService.ts::startCodexDeviceAuth → Tauri invoke codex_oauth_device_auth_start → src-tauri/src/commands/codex.rs::codex_oauth_device_auth_start → src-tauri/src/modules/codex_oauth.rs::start_device_auth`.

`src-tauri/src/lib.rs` registers `commands::codex::codex_oauth_device_auth_start` in the Tauri invoke handler.

Classification: **P1 SOURCE-CHARACTERIZED / ADOPTION DECISION OPEN**. HMS does not need to pretend this feature existed in the v1.3.28 evidence epoch. Before adopting v1.3.29, HMS must explicitly choose whether device auth is required parity for its Codex-only scope or an accepted documented capability gap, with cancellation/timeout/restart semantics preserved if implemented.
